### 1. 💡 RGB LED індикація стану на 10% яскравості

#### Опис концепції
Використання вбудованого адресного RGB світлодіода (WS2812B/NeoPixel на GPIO 48 або GPIO 38) на платі ESP32-S3 для візуального відображення поточного стану пристрою без необхідності відкривати браузер чи підключати USB. Обмеження яскравості до 10% (значення 15–25 з 255) повністю усуває нагрів кристала і споживає менше 2 мА.

#### Кольорове кодування:
- 🔵 **Синій повільний пульс:** підключення до Wi-Fi / режим AP Captive Portal.
- 🟡 **Жовтий статичний:** пошук стрімера / авторизація в Twitch.
- 🟢 **Зелений плавний "дихаючий" (Breath):** активний фармінг (успішні Heartbeat).
- 🟣 **Фіолетовий короткий спалах:** успішно забрано дроп (Claim) або зібрано бали каналу.
- 🔴 **Червоний:** помилка Wi-Fi, недійсний токен або бан сесії.

#### ➕ Плюси:
- Миттєва фізична діагностика роботи пристрою.
- Мінімальне енергоспоживання (~0.01 Вт) і відсутність нагріву.
- Можливість додати перемикач «Нічний режим / LED Off» у веб-інтерфейс.

#### ➖ Мінуси та ризики:
- Різні виробники плат (Espressif, LilyGO, Waveshare, noname клони) використовують різні піни для RGB LED (GPIO 48, 38, 21 або звичайний одноколірний LED). Потрібно зробити пін налаштовуваним або детектувати автоматично.

#### ⚖️ Порівняння з Python-аналогом:
У ПК-версіях це реалізується через іконку в треї Windows. На мікроконтролері апаратний LED — ідеальний аналог трей-іконки.

#### 🎯 Вердикт: **10/10 — Реалізувати рекомендується.**

### 2. 🎁 Автоматичний збір Channel Points (Балів каналу)

#### Опис концепції
На Twitch кожні 15–20 хвилин на стрімі з'являється зелена кнопка/скриня бонусних балів каналу (+50 балів). Коли ця скриня стає доступною, Twitch надсилає повідомлення у WebSocket PubSub топік `community-points-user-v1.<USER_ID>`. ESP32 перехоплює подію `claim-available`, витягує `claim_id` і надсилає GraphQL мутацію `ClaimCommunityPoints`.

```graphql
mutation ClaimCommunityPoints($input: ClaimCommunityPointsInput!) {
  claimCommunityPoints(input: $input) {
    pointsEarned
    claimStatus
  }
}
```

#### ➕ Плюси:
- **0 додаткового трафіку:** подія надходить через уже відкритий PubSub WebSocket.
- **Підвищення "Trust Score" акаунта (Stealth):** боти, які лише шлють Spade-телеметрію, ніколи не збирають бали каналу. Кліки по скринях імітують активного живого глядача.
- Накопичення балів каналу для улюблених стрімерів під час фармінгу дропів.

#### ➖ Мінуси та ризики:
- Для мутації `ClaimCommunityPoints` Twitch іноді вимагає валідний `Client-Integrity` токен (який у нас уже реалізований).

#### ⚖️ Порівняння з Python-аналогом:
У *TwitchDropsMiner* ця функція є однією з найпопулярніших і працює за абсолютно ідентичним принципом.

#### 🎯 Вердикт: **9.5/10 — Реалізувати обов'язково.**

### 3. ⚡ Відмова від HTTP-полінгу на користь Event-Driven моделі

#### Опис концепції
Зараз пристрій кожні 2–5 хвилин надсилає важкий GraphQL-запит `Inventory` для перевірки відсотків. При Event-Driven моделі пристрій підписується на `user-drop-events.<USER_ID>` у PubSub і отримує пуш-сповіщення при зміні прогресу на кожен 1% і при досягненні 100%.

#### ➕ Плюси:
- Економія до 80% викликів GraphQL API.
- Економія RAM (не потрібно десеріалізувати великі відповіді інвентаря).
- Зниження ризику отримати статус `HTTP 429 Too Many Requests`.
- Миттєвий клейм нагороди в ту ж секунду, коли досягнуто 100%.

#### ➖ Мінуси та ризики:
- **Нестабільність WebSockets:** Якщо інтернет короткочасно пропадає або Twitch скидає сокет, повідомлення про 100% може бути втрачено, і без полінгу пристрій не дізнається про завершення дропу.
- **Рішення (Гібридна модель):** Зробити Event-Driven основним джерелом, але залишити "Fallback Polling" раз на 15–20 хвилин як страховку.

#### 🎯 Вердикт: **9.0/10 — Впровадити в гібридному режимі (Event-First + рідкісний Fallback).**

### 4. 🛡️ Jitter (Ентропія та плаваючі таймери фармінгу)

#### Опис концепції
Анти-фрод системи Twitch аналізують регулярність відправки пінгів перегляду. Справжній браузер ніколи не відправляє пінг рівно раз на 60.000 секунд через таймінги рендерингу вкладки, мережеві затримки та буферизацію HLS.

Замість `delay(60000)` впроваджується апаратна ентропія ESP32 TRNG:
$$\Delta t = 56000 + (\text{esp\_random}() \pmod{12000}) \text{ мс} \quad (56 \dots 68 \text{ сек})$$

#### ➕ Плюси:
- Повне усунення виявлення за патерном таймінгів телеметрії.
- Реалізується у 2–3 рядки коду без жодного навантаження на систему.

#### ➖ Мінуси:
- Відсутні.

#### 🎯 Вердикт: **10/10 — Однозначно реалізувати.**

### 5. 🔌 HTTP Keep-Alive та TLS Session Resumption

#### Опис концепції
Кожен новий запит до `gql.twitch.tv` вимагає встановлення TLS 1.2/1.3 сесії (рукопотискання ECDH + RSA), що на процесорі ESP32 займає **1.2–2.0 секунди** обчислень.

#### Технічні особливості на ESP32:
1. **HTTP Keep-Alive (Persistent Socket):** Edge-сервери Twitch (Cloudflare) закривають сокет через 5–15 секунд неактивності. Оскільки Spade надсилається раз на хвилину, чистий Keep-Alive сокет буде постійно закриватися сервером за таймаутом.
2. **TLS Session Resumption (Session Tickets / Session ID):** Бібліотека `WiFiClientSecure` підтримує збереження сесії mbedTLS. При наступному підключенні замість повного Handshake виконується спрощений (Abbreviated Handshake), що займає **менше 80 мс** замість 1800 мс!

#### ➕ Плюси:
- Зниження навантаження на CPU ядро в 10+ разів під час мережевих запитів.
- Зменшення енергоспоживання та нагріву мікроконтролера.

#### ➖ Мінуси:
- Потребує приблизно 2-4 КБ оперативної пам'яті для збереження контексту TLS-сесії.

#### 🎯 Вердикт: **8.5/10 — Реалізувати через TLS Session Resumption.**

### 6. 💾 Захист Flash-пам'яті (NVS Wear Leveling / RTC RAM)

#### Опис концепції
Flash-пам'ять має ліміт ~100 000 циклів перезапису на сектор. Постійний щохвилинний запис поточних відсотків дропу або хвилин перегляду у Flash NVS призведе до деградації пам'яті через кілька місяців безперервної роботи.

#### Рішення:
1. Зберігати поточний прогрес, ім'я стрімера та статус у **RAM / RTC Slow Memory** (пам'ять, яка не стирається при софт-перезавантаженнях).
2. Записувати в фізичну **Flash NVS** виключно у випадках:
   - Зміна налаштувань користувачем у Web UI / CLI.
   - Завершення гри (100%) та перемикання черги на наступну.
   - Додавання нової гри в пріоритет.

#### ➕ Плюси:
- Нескінченний термін служби Flash-пам'яті ESP32.
- Миттєва робота без мікрофризів на запис у флеш.

#### 🎯 Вердикт: **10/10 — Однозначно необхідно.**

### 7. 💤 Розумний режим сну (Deep Sleep vs Light Sleep)

#### Опис концепції
Коли всі дропи зібрано, а наступна кампанія починається лише через 8–12 годин, пристрій переходить у режим сну до мітки часу `startAt`.

#### Порівняння режимів сну:
- **Deep Sleep:** Споживання **10–20 мкА**. Але при цьому **повністю вимикається Wi-Fi та Web-сервер**. Пристрій не буде відкривати веб-сторінку, доки не настане час пробудження (або доки користувач не натисне кнопку перезавантаження).
- **Light Sleep / Modem Sleep:** Споживання **15–25 мА** (проти 120–160 мА при активній роботі). Wi-Fi залишається підключеним за протоколом DTIM, Web-сервер продовжує відповідати, але процесор спить між подіями.

#### 🎯 Рекомендація:
Для пристрою з локальним Web Dashboard найкраще використовувати **Modem Sleep / Light Sleep** або циклічне опитування з інтервалом у 30-60 хвилин, щоб користувач завжди мав доступ до веб-панелі.

#### 🎯 Вердикт: **8.0/10 — Реалізувати у формі Modem Sleep / Idle Cooldown.**

### 8. 🔄 Безшовне слідування за рейдами (Raid Following)

#### Опис концепції
Коли стрімер завершує трансляцію, він часто надсилає рейд на інший канал. Twitch надсилає подію рейду через PubSub (`raid.<CHANNEL_ID>`). ESP32 може миттєво підхопити новий канал без очікування 15-хвилинного таймауту відсутності прогресу.

#### Підводні камені:
- Необхідно перевіряти, чи рейд спрямований на канал, де грають у **ту ж саму гру** та чи ввімкнено Drops на каналі-отримувачі. Якщо стрімер зарейдив іншу категорію, потрібно відхилити рейд і запустити звичайний авто-пошук стрімера для поточної гри.

#### 🎯 Вердикт: **8.5/10 — Дуже корисна функція, варто додати з перевіркою категорії.**

### 9. 📦 Стрімінговий парсер JSON (Streaming/SAX) проти DOM

#### Опис концепції
Потоковий парсер читає байти з мережевого сокета послідовно, не завантажуючи весь масив тексту у пам'ять.

#### Чи потрібен він на ESP32-S3?
- На стандартному ESP32 (520 КБ RAM) це було б обов'язковим.
- На нашій платі **ESP32-S3 (N16R8)** встановлено **8 МБ PSRAM**. Виділення 100 КБ буфера під `JsonDocument` у PSRAM займає менше 1.5% доступної пам'яті і виконується за лічені мілісекунди.
- Стрімінговий парсер вимагає написання громіздкого коду кінцевих автоматів (State Machine) для кожного поля.

#### 🎯 Вердикт: **7.0/10 — Не є критичним для плати з 8MB PSRAM, поточний ArduinoJson у PSRAM надійніший та простіший у підтримці.**

### 10. 🎮 Авто-фарм усіх прив'язаних кампаній (Linked Account Campaigns)

#### Опис концепції
Автоматичне виявлення в `ViewerDropsDashboard` усіх кампаній, які:
1. Мають статус `ACTIVE` і не закінчилися (`endsAt > now`).
2. Мають статус прив'язки акаунта (`isAccountLinked: true`).
3. Ще не завершені (прогрес < 100%).

Якщо черга користувача порожня або всі пріоритетні ігри завершено, ESP32 автоматично по черзі фармить усі такі кампанії.

#### ➕ Плюси:
- Повний режим "увімкнув і забув": ESP32 збере всі можливі нагороди без жодної ручної взаємодії.

#### 🎯 Вердикт: **9.5/10 — Реалізувати обов'язково.**

### 11. 🎯 Список пріоритетних стрімерів, прив'язаних до гри або кампанії (Per-Game / Per-Campaign Streamer Whitelist)

#### Опис концепції
Зараз параметр цільового стрімера (`target_channel`) єдиний і глобальний для всієї прошивки. Це створює дві проблеми:
1. Якщо задати стрімера для GTA V, то при перемиканні черги на Rust пристрій намагатиметься дивитися стрімера GTA V, доки користувач вручну не виконає `channel clear`.
2. Багато кампаній на Twitch мають **ексклюзивні дропи** (Streamer-specific / Tournament drops), які зараховуються лише на 1–3 конкретних каналах або вимагають перегляду конкретного партнера.

#### Запропоноване архітектурне рішення:
Розширення структури гри у черзі (`GameEntry`), де кожна гра зберігає власний список пріоритетних стрімерів (Fallback Whitelist):
```cpp
struct GameEntry {
    char name[48];
    uint8_t priority;
    uint8_t status;
    uint8_t progress_pct;
    uint16_t minutes_watched;
    char preferred_streamers[3][32]; // До 3 пріоритетних стрімерів для цієї гри
    uint8_t streamer_count;
};
```

#### Логіка вибору каналу при фармінгу гри:
1. **Етап 1 (Перевірка Whitelist):** Пристрій по черзі опитує стрімерів зі списку `preferred_streamers` для поточної гри (чи стрімер онлайн, чи грає в потрібну гру та чи активні Drops).
2. **Етап 2 (Fallback):** Якщо перший стрімер офлайн, автоматично перевіряється другий і третій.
3. **Етап 3 (Auto-Discovery):** Якщо жоден із бажаних стрімерів не веде трансляцію, ESP32 автоматично шукає найпопулярнішого загального стрімера з тегом `DropsEnabled` у цій категорії гри.
4. **Підтримка CLI та Web UI:**
   - Команди: `game streamer add <game_name> <streamer_login>`, `game streamer list <game_name>`, `game streamer clear <game_name>`.
   - У веб-панелі: зручне поле введення бажаних каналів під кожною грою в черзі.

#### ➕ Плюси:
- Повна незалежність ігор у черзі: кожна гра має своїх стрімерів.
- Безперебійний перехід на резервного стрімера (Fallback), якщо улюблений автор пішов офлайн.
- Можливість гарантовано фармити ексклюзивні турнірні та промо-кампанії.

#### ➖ Мінуси та нюанси:
- Незначне збільшення розміру структури конфігурації в NVS Flash (при 8 іграх по 3 стрімери — додатково ~768 байт, що для 16MB Flash мізерно).

#### 🎯 Вердикт: **9.5/10 — Реалізувати обов'язково (вирішує ключову проблему гнучкості черги).**

### 12. 👥 Мульти-акаунтний фармінг (Multi-Account Profile Management & Round-Robin)

#### Опис концепції
Підтримка збереження та обслуговування кількох облікових записів Twitch (наприклад, від 2 до 4 акаунтів: основний + твінки) на одному мікроконтролері ESP32-S3.

#### Моделі реалізації мульти-акаунтів на ESP32-S3:

1. **Режим черги акаунтів (Sequential / Round-Robin Farming) [РЕКОМЕНДОВАНИЙ]:**
   - Кожен акаунт має власний профіль: OAuth-токен, ім'я користувача, Device ID, власний список ігор/прогресу та лічильники.
   - **Сценарії ротації:**
     - *За часом (Time Slice):* Наприклад, 2 години фармінгу на Акаунті 1 -> авто-перемикання на Акаунт 2.
     - *За завершенням дропу (Drop Completion):* Акаунт 1 забирає доступний дроп (100%) -> перемикання на Акаунт 2 для отримання того ж дропу.
     - *За кампаніями:* Акаунт 1 збирає всі дропи гри A, а Акаунт 2 — гри B.
   - При перемиканні пристрій коректно закриває WebSocket PubSub попереднього акаунта, генерує/підставляє Client-Integrity токен для нового акаунта та підключає нову сесію.

2. **Ручний перемикач профілів (Profile Switcher у Web UI):**
   - Збереження профілів у пам'яті (наприклад, "Main", "Alt_1", "Alt_2").
   - Перемикання активного профілю в один клік у веб-інтерфейсі без повторного ручного введення токенів.

3. **Паралельний (Concurrent) фармінг кількох акаунтів (Чому НЕ рекомендується):**
   - Відправка хвилинних Heartbeat-запитів для кількох акаунтів одночасно з однієї IP-адреси та однакового TLS Fingerprint викликає підозру в системі безпеки Twitch (Spade/Telemetry Anti-Bot) і може призвести до тіньового бану нарахування дропів для всіх акаунтів.
   - Послідовний режим (Round-Robin) з Jitter-паузою між зміною сесій є на 100% безпечним (Stealth).

#### Структура профілю акаунта в пам'яті:
```cpp
struct AccountProfile {
    char profile_name[24];      // "Main", "Alt"
    char oauth_token[80];       // Токен авторизації
    char user_id[20];           // Twitch ID
    char user_login[32];        // Логін користувача
    char device_id[36];         // Унікальний Device ID для цього акаунта
    bool enabled;               // Чи бере участь в авто-ротації
    uint32_t total_minutes;     // Статистика
    uint16_t drops_claimed;     // Кількість нагород
};
```

#### ➕ Плюси:
- Фармінг нагород для всіх своїх акаунтів на одному пристрої без необхідності купувати додаткові плати ESP32.
- Швидке перемикання профілів через Web UI або CLI (`account switch <id>`, `account list`).
- Безпечна ротація сесій з повною ізоляцією WebSocket та токенів цілісності.

#### ➖ Мінуси та ризики:
- Необхідність зберігати кілька OAuth-токенів у NVS Flash (потрібне надійне шифрування/маскування).
- Додатковий код для менеджменту сесій та стану підписок PubSub.

#### 🎯 Вердикт: **9.0/10 — Реалізувати в режимі Profile Switcher + Round-Robin Rotation.**

### 13. 🌐 Статичні Fallback DNS та авто-відновлення Wi-Fi з'єднання

#### Опис концепції
Збої DNS (`DNS Failed for gql.twitch.tv / spade.twitch.tv`) часто виникають на мобільних точках доступу, USB-модемах та роздачах з ноутбуків через нестабільність вбудованого DHCP DNS-резолвера.
При підключенні до Wi-Fi примусово призначаються надійні глобальні Anycast DNS сервери (Cloudflare `1.1.1.1` та Google `8.8.8.8`).

```cpp
IPAddress primaryDNS(1, 1, 1, 1);    // Cloudflare DNS
IPAddress secondaryDNS(8, 8, 8, 8);  // Google DNS
WiFi.config(INADDR_NONE, INADDR_NONE, INADDR_NONE, primaryDNS, secondaryDNS);
```

Також додається перевірка стану інтернету: якщо 3 послідовні запити завершуються помилкою DNS (`HTTP Code: -1`), викликається м'який перезапуск Wi-Fi (`WiFi.reconnect()`).

#### ➕ Плюси:
- Повне усунення помилок `hostByName()` на мобільних роздачах та хотспотах.
- 0 додаткового навантаження на систему.

#### 🎯 Вердикт: **10/10 — Критично необхідно (усуває реальну проблему з логів).**

### 14. ⏱️ Захист від підвисань: HTTP Timeouts (7s) та Task Watchdog Timer (TWDT)

#### Опис концепції
При поганій якості сигналу Wi-Fi або скиданні SSL-сесій сервером Twitch стандартні функції HTTPClient можуть блокувати FreeRTOS таску на 15–30 секунд. Це викликає спрацьовування апаратного сторожового таймера ESP32 (Task Watchdog) і раптове перезавантаження мікроконтролера (`RTC_SW_CPU_RST`).

#### Заходи захисту:
1. Встановлення жорсткого таймауту для всіх клієнтів: `http.setTimeout(7000)` (7 секунд).
2. Явне скидання TWDT (`esp_task_wdt_reset()`) перед і після важких TLS-запитів.
3. Неблокуюча обробка помилок із плавним відкатом до наступного циклу.

#### ➕ Плюси:
- 100% захист від раптових рестартів при нестабільному Wi-Fi.

#### 🎯 Вердикт: **10/10 — Критично необхідно.**

### 15. 🔄 Розумне керування сесіями HLS Usher (Миттєве скидання кешу на 403/404)

#### Опис концепції
Посилання на відеопотік Usher (`usher.ttvnw.net`) вимагають `PlaybackAccessToken` (`sig` + `token`). Коли стрімер перезапускає трансляцію або токен вичерпує свій термін дії, сервер повертає `HTTP 403 Forbidden` або `HTTP 404 Not Found`. Якщо клієнт продовжує пінгувати застарілий `Session ID`, перегляди не зараховуються, а пристрій вважає стрімера "офлайн".

#### Рішення:
При отриманні будь-якого статус-коду `HTTP 403 / 404` від Usher або Spade:
1. Миттєво анулювати `cachedAccessToken` та `cachedSessionId`.
2. Примусово виконати новий GQL-запит `PlaybackAccessToken` перед наступним Heartbeat.

#### ➕ Плюси:
- Усуває помилкові ротації стрімерів при короткочасному перезапуску трансляцій.

#### 🎯 Вердикт: **10/10 — Критично необхідно.**

### 16. 💾 Виділення пам'яті в PSRAM та фільтрація JSON (Zero Heap Fragmentation)

#### Опис концепції
При великій кількості ігор на Twitch (наприклад, 50+ кампаній у `ViewerDropsDashboard`) розмір відповіді досягає 40–80 КБ. Парсинг такого об'єму у внутрішній SRAM може спричинити фрагментацію пам'яті та збій `deserializeJson()`.

#### Рішення:
1. Використання 8 МБ PSRAM для великих JSON-документів через спеціальний алокатор ArduinoJson:
   `SpiRamJsonDocument doc(65536);`
2. Застосування фільтра десеріалізації (`DeserializationOption::Filter`), який завантажує в пам'ять лише критичні поля (`id`, `name`, `status`, `currentMinutesWatched`), відсікаючи 70% непотрібних метаданих (описи, зображення, посилання).

#### ➕ Плюси:
- Нульовий ризик переповнення пам'яті при будь-якій кількості активних кампаній на Twitch.
- Прискорення парсингу JSON на 40%.

#### 🎯 Вердикт: **9.5/10 — Однозначно варто реалізувати.**

### 17. 📲 Web OTA Updates (Оновлення прошивки по Wi-Fi через браузер)

#### ➕ Плюси:

### 18. 🛡️ Адаптивність до змін Twitch API (Динамічні GQL Hashes та Integrity Fallback)

#### Опис концепції
Twitch періодично модифікує хеші GraphQL-операцій (як це відбулося з `ClaimDrop`). Щоб пристрій не втрачав працездатність при наступній зміні API Twitch, впроваджується:
1. Збереження хешів операцій (`DropsPage_ClaimDropRewards`, `PlaybackAccessToken`, `ViewerDropsDashboard`) у конфігурації NVS із можливістю оновлення через Web UI або CLI без перепрошивки коду.
2. Автоматичний Fallback: якщо запит із `persistedQuery` повертає помилку `PersistedQueryNotFound` — автоматично виконувати повторний запит із відкритим текстом мутації (Inline Query).

#### ➕ Плюси:
- Повний захист від раптових змін на серверній стороні Twitch.

#### 🎯 Вердикт: **9.0/10 — Варто додати.**
